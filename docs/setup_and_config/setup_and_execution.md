# Setup and Execution

This document covers everything you need to install the dependencies, prepare your environment, configure the parameters, and run the pipeline end-to-end.

## 1. Installation

### 1.1 Clone and Access the Repository

For GitLab authentication details (PAT creation, clone from VS Code, and credential persistence), see [GitLab Access and Usage Guide](gitlab.md).

```bash
git clone https://umane.emeal.nttdata.com/git/analytics/projects/health/ends-pt/herramienta-datos-sinteticos.git
cd herramienta-datos-sinteticos
```

### 1.2 Automated Setup (Windows & Linux)

The repository provides automated scripts that install **uv**, an isolated **Python 3.12.3** installation, and construct two virtual environments (`.venv_core` and `.venv_eval`).

> **Recommendation for Windows users:** We recommend using **WSL** over PowerShell  as all scripts are originally designed for Linux-like environment. See [Quick Setup on WSL](wsl_setup.md).

#### Linux / macOS / WSL
```bash
make setup
```

#### Windows (PowerShell)
```powershell
.\scripts\setup.ps1
```

---

### 1.3 Makefile (Linux / macOS / WSL)

On Linux-like systems the `Makefile` is the easy-to-use entry point — it drives setup, execution, listing utilities, and lint/format:

```bash
make help
make setup
make train
make pipeline CONFIG=config/pipelines/my_pipeline.yaml
make format
```

Commands like `make train`, override any EXECUTION_MODE defined in execution_configuration.py to run main in that specific mode.

Windows users should use `scripts/setup.ps1` and `scripts/run.ps1` (or switch to WSL).

## 2. The `config/` Directory

The repository utilizes various configuration files defined in `config/`.

> **For a basic run, the ONLY thing you must configure is the `DEFAULT_DATA_PATH` inside `config/general_config.py`.**

Below is a detail of each configuration file and what they control.

### 2.1 `general_config.py`
This is your master configuration file. It dictates global paths, evaluation metrics to calculate, and core fallback behaviors.

* **Essential for Users to Touch:**
  - `DEFAULT_DATA_PATH`: Where your input CSV/Parquet/Excel files reside.
    - Example: `DEFAULT_DATA_PATH = "data/sintetico"`
    - If you are running locally with heavy files, you may consider making a symlink for `data/` instead of moving data into the repository folder.
* **Generally No Need to Touch:**
  - `OUTPUTS_ROOT`, `MODELS_DIR`, `SIMULATIONS_DIR`: Where artifacts are deployed.
  - System tracking directories or MLflow namespaces.

### 2.2 `execution_config.py`
Configures the execution of the code, which is non-interactive.

* **What it Does:** Configures `mode`, `file_paths`, `sample_size`, `model_id`, `inspection_id` and `simulation_id` parameters. You must configure your run here prior to executing `make <mode>` (Linux/macOS/WSL) or `run.ps1` (Windows).
* **Finding IDs:** Call the list functionalities (within your `.venv_core` virtual environment):
  - **Inspections**: `python -m src.core.list_available_inspections --format table`
  - **Models**: `python -m src.core.list_available_models --format table`
  - **Simulations**: `python -m src.core.list_available_simulations --format table`

### 2.3 `mostly_ai_config.yaml`
Parameters passed to the deep learning architecture of Mostly AI.

* **What it Does:** Dictates engine parameters (e.g. `max_epochs`, `max_training_time`, `batch_size`) and privacy layers (`differential_privacy`).
* **When to Touch:**
  - You encounter RAM constraints and need to lower `batch_size`.
  - You require an expedited, low-quality test run so you lower `max_epochs: 1` or cap `max_training_time`.
  - You are experimenting with distinct Differential Privacy strictness.

### 2.4 `rules.yaml`
Logical validation rules mapped explicitly onto the datasets to restrict anomalies generated by ML models.

* **How to Setup Rules:**
  - Open `rules.yaml` and append objects to the `rules` array.
  - Define `type` (e.g., `date_inequality`, `semantic_ranking_consistency`).
  - Target your custom tables (`table_origin`, `table_target`) and map the constraint columns.
* **When to Touch:**
  - Every time you introduce a new table relationship or business rule that must not be violated by synthetic generation.

### 2.5 `evaluation/evaluation_config.py`
Centralizes parameters for metrics, statistical evaluation, and the evaluation subprocess environment.

* **Essential for Users to Touch:**
  - `EVAL_DEFAULT_METRICS`: List of metrics to be calculated for each table. To disable heavy metrics like `DomiasMIA_BNAF`, comment them out here.
  - `EVAL_PYTHON_PATH`: Path to the isolated virtual environment interpreter.
* **Generally No Need to Touch:**
  - Confidence levels, bootstrap sample sizes, and other statistical parameters.

### 2.6 `evaluation/statistics.yaml`
Governs how custom dataset statistics are captured and evaluated.

* **What it Does:** Instructs the evaluation phase to calculate baseline statistics (`mean`, `median`, `variance`, `skewness` or arbitrary formulas like `np.log({col})`) across specific tables and columns.
* **When to Touch:** When measuring the fidelity of complex transformations.

## 3. Execution

Execution is non-interactive: the tool reads parameters from `config/execution_config.py`.

### 3.1 Modes

| Flag | Mode | Purpose |
|------|------|---------|
| `i`  | Inspect  | Load + preprocess + autodetect metadata. Stops before training so you can review/edit the schema. |
| `t`  | Train    | Train a generator (from raw files or from a previous inspection). |
| `s`  | Simulate | Generate synthetic data from a trained model. |
| `e`  | Evaluate | Compare synthetic data against original. |
| `p`  | Pipeline | Run the full end-to-end pipeline. |

### 3.2 Running the Tool

```bash
# Linux / macOS / WSL
make inspect    
make train      
make simulate   
make eval       
make pipeline CONFIG=config/pipelines/my_pipeline.yaml   # mode p
```

Run `make help` to see every available target.

```powershell
# Windows (PowerShell)
.\scripts\run.ps1 <mode>
```

## 4. Recommended End-to-End Flow

Running training directly works, but the **inspect → review → train** flow lets you fix autodetected relationships through PKs/FKs and encoding types without running for a full training cycle.

### Step 1 — Inspect
Set `FILE_PATHS`, then run:
```bash
make inspect
```

Loads, preprocesses, autodetects and writes the session under `outputs/inspections/inspection_<timestamp>/`.

### Step 2 — List sessions
```bash
make inspections
```
Copy the `inspection_id` you want to train from.

### Step 3 — Review and edit
Inside `outputs/inspections/<inspection_id>/`:
- **`autodetect.json`** — **the only source of truth** for PKs/FKs and encoding types. Edit here to fix the schema.
- `inspection_card.json` — session descriptor (inputs, configs, table sizes). Rename the session by editing its `inspection_name`.
- `metadata.json` — preview only; regenerated from `autodetect.json` at training time (editing it has no effect).
- `processed_data/*.parquet` — cached tables reused at training time.

### Step 4 — Train from the inspection
Set `INSPECTION_ID = "inspection_..."`, then:
```bash
make train
```
Preprocessing is skipped; training consumes the cached parquet + your edited `autodetect.json`.

### Step 5 — Simulate
List models, then set `MODEL_ID = "model_..."` and optionally `SAMPLE_SIZE`:
```bash
make models
make simulate
```

### Step 6 — Evaluate
List simulations, then set `SIMULATION_ID = "simulation_..."`:
```bash
make simulations
make eval
```
